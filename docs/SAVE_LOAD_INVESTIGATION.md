# Continue/save-load investigation (no save-behaviour change)

The reported launch skipped the main menu through FusionFix and used automatic Continue. It was **not a manually selected wrong slot**. Reported save-file writes occurred before installation and cloud metadata was written later. Private profile identifiers and exact activity times are deliberately omitted from public source and PR text.

## What code inspection establishes

- The project ASIs use executable-relative INI/log paths and game audio metadata. No code opens SGTA save files, ProfileSettings, cloudsavedata.dat or Documents/Rockstar Games/GTA IV. No project game-native call selects a save slot or invokes a save/load routine. Runtime hooks concern HUD/navigation, pause/audio, map zoom and the documented settings/menu interfaces; this is code inspection, not proof against every possible game/mod interaction.
- The bundle helper stages a fixed allowlist of ASIs/INI and the verified FusionFix host beside the executable/root/plugins/scripts, with game-local backups, duplicate handling and rollback. FusionFix assets go under the game folder. Updater, upload helper and caches use their own .config/.local/.cache directories. No project file move, timestamp edit or cloud-sync operation targets saves/profiles. Existing FusionFix settings are retained; fresh missing settings use the official dependency defaults.
- The installer reads Steam libraries/configuration, existing prefix DLLs/registry and compatibility metadata. It does **not** rewrite Steam's app compatibility selection, change the game's launch command to a different prefix, set Windows user/profile identity, or create a replacement game prefix. It does run Proton for Microsoft runtime setup and the loader registry override in an existing prefix.
- That last point prevents an absolute claim that nothing involved can touch Documents: [Valve Proton initialization](https://github.com/ValveSoftware/Proton/blob/proton_10.0/proton#L883) includes user-folder/symlink migration between My Documents and Documents, and prefix upgrades. The old installer offered a manual choice among installed Proton versions; selecting a different one could initialize/upgrade that same prefix. This is a plausible indirect mechanism, **not evidence it happened in this session or selected an older save**. The present installer UX change reads Steam's configured tool automatically and uses the existing app prefix; no save-specific repair or migration was added.

## What FusionFix Continue does, and what remains unverified

The pinned FusionFix 5.1.2 [skipintro.ixx](https://github.com/ThirteenAG/GTAIV.EFLC.FusionFix/blob/cad0970e2c82712d86c849974b62d078331ddd88/source/skipintro.ixx#L12) changes the original startup argument from 0 to 6 when SkipMenu is enabled (unless Shift suppresses it), then calls the original game function. This is the observed auto-Continue path. It neither scans save files nor compares file modification times nor writes a last-slot pointer itself. The QoL menu adaptation does not patch that startup function.

The full FusionFix dependency also contains upstream save-related changes, such as [allowing ACTIVATE_SAVE_MENU in vehicles](https://github.com/ThirteenAG/GTAIV.EFLC.FusionFix/blob/cad0970e2c82712d86c849974b62d078331ddd88/source/fixes.ixx#L1162). That patch is not a Continue ranking implementation and is not changed by this PR; the bundle should not be described as having no save-related external dependencies at all.

The original GTA IV Complete Edition Continue selector is proprietary game code, not included in this repo. No game executable/disassembly, profile bytes, before/after file hashes or runtime load trace is available here. Inspection therefore cannot establish whether that selector ranks filesystem times, embedded save metadata, a remembered slot/episode/profile preference, or some combination. **Do not claim “Continue always loads the newest filesystem timestamp,” “ProfileSettings definitely contains a stale pointer,” or “cloudsavedata.dat proves a restore.”** No source found here establishes those claims. The public save-format parser inspected during research documents payload fields, not the game's Continue algorithm.

Recent modification times show writes/touches, not which save content/slot/profile Continue resolved to. Two similarly timed files do not establish their internal mission/clothes state or selection order. A later cloud-metadata write alone cannot prove or exclude a cloud restore. An older auto-Continue-resolved slot/state, different active profile/prefix/episode, or sync restoration remain hypotheses, not findings. The correction rules out blaming a manual slot choice.

## Conclusion and evidence needed

No direct save/profile/cloud access or slot-selection mechanism was found in this project's code, and no save behaviour is changed in this PR. The symptom is unresolved; an absolute “installer cannot indirectly affect the save environment” claim would be too strong because it invokes external Proton and includes FusionFix's startup flow.

A decisive follow-up would correlate the game's loaded slot/episode/profile and displayed save mission/in-game time with read-only save/header hashes and Steam/Rockstar sync history before/after startup, plus the actual configured Proton and active prefix. Existing timestamps alone are insufficient. This is an investigation result, not an instruction to edit, delete, restore, re-save or disable cloud settings. A player can inspect the pause-menu Load overview without choosing a slot; deeper evidence should be collected by a separate consented diagnostic, not manual save-file manipulation.
